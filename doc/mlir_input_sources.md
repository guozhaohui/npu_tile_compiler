# MLIR Input: Hand-Written vs Generated

In real projects, hand-written `.mlir` files are used almost exclusively for **testing and debugging**.
Production IR is always generated by a tool.

## Frontend compiler generates MLIR directly

For custom compilers or DSLs, the compiler frontend calls the MLIR C++ `OpBuilder` API to emit IR
programmatically. End users never touch `.mlir` files.

## Import tools translate existing IRs into MLIR

| Source            | Tool                                       |
|-------------------|--------------------------------------------|
| PyTorch models    | `torch-mlir` (`torch-mlir-opt`, `torch_mlir.compile()`) |
| TensorFlow / JAX  | StableHLO / XLA export → MLIR             |
| ONNX models       | `onnx-mlir`                               |
| LLVM IR           | `mlir-translate --import-llvm`            |
| TFLite            | TOSA import via IREE                      |

## Typical NPU/accelerator compiler flow

```
PyTorch / ONNX model
        ↓  (torch-mlir or onnx-mlir)
High-level MLIR (linalg / tosa / stablehlo)
        ↓  (lowering passes, e.g. --lower-my-to-npu)
Custom hardware dialect (npu.*)
        ↓  (codegen / scheduling passes, e.g. --npu-tiling)
Binary / assembly for the NPU
```

## Where hand-written `.mlir` files are still used

### lit / FileCheck tests (standard MLIR testing methodology)

Each `.mlir` file has embedded `// RUN:` and `// CHECK:` directives, run automatically by `llvm-lit`.
This is how all upstream MLIR passes are tested.

```mlir
// RUN: my-opt --lower-my-to-npu %s | FileCheck %s
// CHECK: npu.compute_add

func.func @test(%a: i32, %b: i32) -> i32 {
  %0 = my.add %a, %b : i32
  return %0 : i32
}
```

### Debugging

Dump IR mid-pipeline with `--mlir-print-ir-after-all` and inspect or edit it by hand.

## Summary

`test/test.mlir` in this project is a manually written fixture to verify passes work.
For a production NPU compiler, add a frontend (or import from torch-mlir/ONNX) as the real entry point.

# MLIR `matchAndRewrite` Explained

Using `MyAddToNPUComputeAdd` in `lib/LowerMyToNPU.cpp` as the example:

```cpp
struct MyAddToNPUComputeAdd : public mlir::OpRewritePattern<my::MyAddOp> {
  using OpRewritePattern::OpRewritePattern;

  mlir::LogicalResult
  matchAndRewrite(my::MyAddOp op, mlir::PatternRewriter &rewriter) const override {
    rewriter.replaceOpWithNewOp<npu::NPUComputeAddOp>(
        op, rewriter.getI32Type(), op.getA(), op.getB());
    return mlir::success();
  }
};
```

## Match (implicit)

The template parameter `OpRewritePattern<my::MyAddOp>` tells the greedy rewrite driver to only
call `matchAndRewrite` when it encounters a `my.add` op. There is no explicit `match()` override
here — the type match is sufficient and always succeeds.

## Rewrite — one call does four things

```cpp
rewriter.replaceOpWithNewOp<npu::NPUComputeAddOp>(
    op,                    // 1. the old op to replace and erase
    rewriter.getI32Type(), // 2. result type of the new op
    op.getA(), op.getB()   // 3. operands forwarded from the old op
);
//                         // 4. all uses of op's result are updated to the new result
```

`replaceOpWithNewOp` is a convenience that combines:
- `rewriter.create<npu::NPUComputeAddOp>(...)` — builds the new op
- `rewriter.replaceOp(op, newOp)` — patches all SSA uses, then erases the old op

## Before / After

```
// Before (my dialect)
%0 = my.add %arg0, %arg1 : i32

// After (npu dialect)
%0 = npu.compute_add %arg0, %arg1 : i32
```

The operands (`%arg0`, `%arg1`) and result type (`i32`) are identical — only the op name changes.
`op.getA()` and `op.getB()` are typed accessors generated by TableGen from the `MyAddOp`
definition in `MyOps.td`.

## Return value

`mlir::success()` tells the driver the rewrite fired. Returning `mlir::failure()` (e.g. after a
precondition check fails) causes the driver to skip this pattern and try the next one.
